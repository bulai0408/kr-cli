## 方法与结果

先把本机真实 `~/.local/state/kr` 整体复制到临时目录，再把
`HOME`、`KR_STATE_DIR` 指向临时位置，分别用基线二进制和新二进制执行
`kr rejudge --json`，不传 `--evidence`，不读取外部结果包。
源目录只读，调用日志只写临时目录。不提交原始日志和个人路径。

| 指标 | 改动前 | 改动后 |
|---|---:|---:|
| rejudge 可读运行数 | 7 | 7 |
| 已保存的结构化判定 | 11 | 11 |
| 相对保存结论的变化 | 0 | 0 |
| 无法读取的判定文件 | 0 | 0 |

两次 rejudge JSON 完全一致。这里比较的是每一轮保存的判定，不是声称
rejudge 已经模拟了“当时不启动整组重跑”的执行路径。

旧运行的整组重跑另用事件和日志离线核对，脚本为
`python3 docs/research/rerun-evaluation.py <复制后的状态目录>`：

| 指标 | 改动前 | 按最终规则回放 |
|---|---:|---:|
| 事件记录的整组重跑 | 40 | 40（保守保留） |
| 日志明确列出同一用例逐个重跑仍失败 | 33 | 33 |
| 这 33 次中有逐个重跑前后正常负载证据、可跳过 | — | 0 |
| 有逐个重跑前后负载采样的旧事件 | 0 | 0 |
| 有整组重跑开始与 item_end 的窗口 | 34 | 34 |
| 上述窗口合计 | 3489.434479 秒 | 3489.434479 秒 |
| 可归因于新规则的节省 | — | 0 秒 |

日志核对只认 `Failing tests:` 下精确匹配的 `Class.method()` 或
`-[Class method()]`，不把 `passed: false`、缺少结果、过滤无效当成确定失败。
缺少逐个重跑采样时，不能借用整个场景的负载推断它在正常环境中执行。

### 两个 preload-ipad 案例

| 运行 | 整组窗口 | 旧结论 | 最终规则 |
|---|---:|---|---|
| `01a13b2f-c14f-76f9-ab4c-fc951e7929c7` | 139.329980 秒 | 整组重跑后通过 | 保留整组重跑 |
| `01a13d19-6586-7649-aa4e-27c26229a032` | 112.425120 秒 | 整组重跑后通过 | 保留整组重跑 |

两次都有逐个重跑再次失败的日志，但都没有逐个重跑的负载采样，负载按未知处理。
最初只看再次失败的方案会跳过 33 次、在 29 个可计时窗口推算少跑
2492.201445 秒，并把这两项原本靠整组重跑恢复的通过留为失败。
协调者据此收紧规则；这些旧方案数字不是最终收益。

### 层级与误差

- 结构化判定：第 3 层确定重放，输入相同，两份输出相同。
- 整组决策：旧日志与事件的离线证据核对；33 个案例缺少负载证据，全部保留，不猜测。
- 时间是整组 `rerun` 到同一运行同一项 `item_end` 的窗口总和，不是整批 makespan。
  另有 6 个窗口缺结束事件，不补估时。没有性能模型校准，不能给出 MAPE 或真实提速比例；
  最终规则在这份证据上不跳过重跑，所以可归因节省为 0。
- 新增逐个重跑采样今后可提供正常负载下再次失败的证据；当前历史不能证明实际收益。
