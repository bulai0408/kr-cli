# kr-cli 规格

2026-10-14，由 owner 与协调者五轮访谈确定。设计理由见 `docs/adr/`，依据见 `docs/research/`。

## 定位

kr 是 owner 个人的开发流程执行层，把 owner 的最佳实践变成可执行、可检查的步骤：按机器性能平衡效率和质量、管理各种环境、让 agent 能放心地自己完成更多事。它与开发工具无关，只支持 Apple 客户端项目。

## 模型

| 部分 | 内容 |
|---|---|
| 机器档案 | 运行时检测能力和状态，推算资源容量；可按机器覆盖（ADR 0003） |
| 环境 | Xcode 版本、模拟器运行时、模拟器池、签名、测试服务器、凭证位置（只记位置） |
| 流程 | 预检 → 构建 → 运行 → 核对 → 门禁，每步产出事件 |
| 信任策略 | 硬底线拦截 / 需要批准 / 自主；按证据建议放宽，由 owner 确认（第三阶段） |
| 适配器 | 远程机器（第二阶段）。kr 不接编排工具和记忆系统（ADR 0002、0007） |

## 第一阶段（P0）

目标：Krill 第 7 批完全用 kr 跑自验和门禁。

### 1. 资源层（ADR 0004）
- 资源 `build`、`sim`、`light`，容量来自机器档案；文件锁槽位，崩溃自动释放。
- 跨项目先来后到队列；`kr queue` 显示占用者（项目、任务、进程、开始时间）、等待者和预计等待时间。
- `kr lock <resource> -- <command>`：拿到槽位后执行一条命令，结束立即归还。

### 2. 机器档案与 `kr doctor`（ADR 0003）
- 检测：芯片、核数、内存、磁盘余量、1/5/15 分钟负载、内存压力、已装 Xcode 与当前选择、模拟器运行时、模拟器池是否齐全。
- 检查项目配置要求的 Xcode 版本和运行时是否存在（避免 Xcode 26/27 混用导致的假红，pitfalls E2/E3）。
- 输出建议的资源容量。负载默认不阻塞：只在内存压力 critical 时等待；每项采样负载，高负载期间的失败整项重跑一次（ADR 0003 补充）。

### 3. 模拟器池
- 每个项目一组 `<项目>-Verify-<N>`，按配置的设备型号和运行时创建；kr 只创建、启动、关闭、抹除池里的设备。
- 租约与 `sim` 槽位绑定，结束时关机归还；同时运行的模拟器数不超过 `sim` 容量。

### 4. 项目配置 `.kr.toml`
- `xcode`：要求的 Xcode 版本（kr 用对应的 `DEVELOPER_DIR` 执行）；`platforms`；`project`（含生成命令，例如 `xcodegen generate`）。
- `suites`：三种步骤——`build`（编译某平台）、`test`（测试目标或包测试，可带过滤）、`command`（任意命令，例如后端测试）。
- `scenarios`：UI 场景注册（名称 → 测试类、所需设备类型如 iPad）。这是场景清单的唯一来源。
- `gates`：命名门禁，由套件和场景组成，例如 `default`、`smoke`。
- `isolation`：测试 bundle 标识与权限要求（用于数据隔离检查）。

### 5. `kr check`（预检，ADR 0005）
不占模拟器，只占 `build` 槽位：
- 运行项目的生成命令；
- 用 App 自身的编译设置真编译：包 scheme 和 App 都用 `build-for-testing -destination generic/platform=…`（不用 `swift build`，ADR 0005 补充）；
- 用测试 bundle 的符号静态核对过滤能匹配到测试（运行时 `kr run` 再做真实枚举，ADR 0005 补充）；
- 数据隔离静态检查：测试用的 bundle 必须是配置里声明的合成标识，权限只能指向允许的环境（例如 CloudKit Development）。
失败就返回非零，agent 不应进入运行队列。

### 6. `kr run` 与 `kr gate`（ADR 0005）
- `kr run <场景|套件...>`、`kr gate [名字]`。
- 构建一次：测试产物按输入哈希缓存；构建完归还 `build`，再按 `sim` 容量租模拟器，按历史耗时分配场景并行运行。
- 超时看门狗：每个场景有硬超时，超时即终止并判失败。
- 运行前枚举测试，0 条即失败；运行后从 xcresult 核对测试数、读取真实退出码。
- 默认 `-collect-test-diagnostics never`、`-skipMacroValidation`。
- 失败的测试单独重跑一次：通过记偶发，仍失败记失败。
- 人读输出：每个场景/套件一行 `PASS:` / `FAIL:`，失败最多 3 行摘要和 xcresult 路径；`--json` 输出结构化结果。

### 7. 事件记录
- 每次运行把事件写到 `~/.local/state/kr/events/` 下的 NDJSON：排队开始、拿到槽位、负载等待、构建开始/结束/缓存命中、场景开始/结束/结果、重跑、归还。
- 第一阶段只记录，不做报告命令；记录要足以算出「排队时间 / 运行时间」和每个场景耗时。

### 第一阶段验收
- 用 Krill 第 7 批实测，对比第 6 批：拿到锁后才发现编译失败 0 次；假通过 0 次；排队时间占比明显下降；计时不再手工拼。
- Krill 仓库加入 `.kr.toml`，`e2e.sh` / `test.sh` 不再需要（kr 不可用时可临时回退旧脚本）。

## 第二阶段（P1）
- **判断骨架（第一张票，ADR 0011）**：判断点结构与专门退出码、`kr decide` 交回决定并记录、事后对账事件、`kr skill`（随版本发布，可按项目和个人追加）。以下各项都建在它上面。
- **选测**：从 `swift package describe --type json` 和工程配置生成模块依赖图；改动文件 → 模块 → 反向闭包 → 场景（场景在配置里声明覆盖的模块）；`--explain` 说明原因；`kr hash` 调试。
- **合并辅助**：`git merge-tree` 预测分支冲突；xcstrings 按键三方合并的 merge driver（合并后用 `xcstringstool` 校验）；为每个 worktree 开启 rerere；合并后秒级快检（JSON 解析、场景清单一致、迁移顺序、改动模块增量编译）；合并后凭证扫描。
- **远程机器**：SSH 资源提供方，远程运行同一个 kr，git 拉取已推送分支，结果回传。

## 第三阶段（P2）
- `kr report`：从事件生成批次效率对比（排队/运行、返工轮数、偶发排行）。
- 偶发隔离区：被隔离的测试照常运行、失败不阻塞，隔离区有上限。
- 交付报告草稿：从 xcresult 生成「机器判定 / 需人判断手感 / 未验证」三段的初稿。
- 信任策略执行：硬底线拦截、批准记录、按证据提出放宽建议。
- 真机流程、签名检查、跨 worktree 编译缓存实验。

## 不做
- 不派单、不和 agent 沟通、不接记忆系统。
- 不判断某台机器允许做什么。
- 不兼容旧脚本的锁协议。
