# 0016 `kr report`：批次按时间范围界定，调用另记一份日志，指标都有固定定义

状态：已采纳（2026-10-15，#33 实现时写，协调者已确认）。

## 背景
spec 第 7 项要 `kr report` 从事件生成批次报告：排队/运行时间、返工轮数、偶发排行、每类判断的判对率，以及 agent 调了哪些命令、参数错几次、哪些判断点判错、在哪里绕了弯。实现前要定下几件事：

- 事件里没有「批次」。Krill 的一批是协调者在一段时间里派出的几张票，合入前后各跑一次检查。
- 第 7、8 批的事件大多早于 #29：没有 `run_start`，也就没有请求者和 worktree；`kr check`、`kr lock` 到现在也不写 `run_start`。
- 事件只记录运行里的步骤（CONTEXT「事件」）。参数错误在 clap 解析时就退出，`kr plan`、`kr queue`、`kr skill` 这类命令不写事件（`kr plan` 有测试保证「不记录任何东西」）。只看事件，算不出「调了哪些命令」「参数错几次」。

## 决定

### 1. 批次 = 一个时间范围里一个项目的运行
- `--since`、`--until`：RFC 3339 时间（`2026-10-14T09:40:00Z`）或相对时长（`90m`、`24h`、`7d`，从现在往前算）。默认最近 24 小时。
- 运行按开始时间（它的第一条事件）归入批次，它的全部事件都算进来，所以跨过 `--until` 的运行不会被截成两半。
- 项目：在项目里默认是这个项目，`--project <名字>` 可以指定，不在项目里且没有指定时包括全部项目。
- `--worktree <路径>`、`--agent <名字>`（都可重复）只保留请求者匹配的运行和调用。没有请求者的运行（#29 之前的运行、`kr check`、`kr lock`）在过滤时被排除，报告写明排除了几个。

理由：时间范围对所有历史事件都能用，而且协调者本来就按时间记批次（派单、合入时间）。kr 不从「空闲间隔」之类的规律去猜批次在哪里分开：猜错了报告就错了，而且没有办法核对（ADR 0011：kr 只做确定的事）。并行的两批（例如第 8 批合入前检查时第 9 批已经开工）只用时间分不开，这时用 `--worktree` 或 `--agent`；对旧事件分不开的，报告写明。

### 2. 调用日志：每次 kr 调用一行，和事件分开存
- 位置：`<状态目录>/invocations/<UTC 日期>.ndjson`，行格式与事件相同，类型为 `invocation`。字段：`command`（子命令，参数解析失败时取第一个不以 `-` 开头的参数，可能为 null）、`args`（除程序名外的全部参数）、`exit_code`、`duration_ms`、`error`（失败时错误信息的第一行）、`requester`（`agent`、`worktree`、`parent_pid`，与 `run_start` 相同）。
- `--help`、`--version` 不记录。写日志失败不影响命令本身。
- 和事件分开存：事件是运行中的步骤，`kr plan` 等命令仍然不写事件；调用日志只给 `kr report` 用。

「参数错误」= 退出码 2（clap 的参数错误，以及 kr 解析后发现的参数错误，例如不存在的判断点 ID）。退出码 1 的错误另算为「kr 报错」，列出错误信息，不归类：例如「不是场景也不是套件」是退出 1，按含义是参数错，但改退出码会改变现有行为，本票不改。

调用日志从这个版本开始才有。时间范围里没有调用日志时，「调了哪些命令」从事件推断（`run_start` / `run_end` 的 label、`step_end` 的 command、`queue_start` 的 task），只覆盖写事件的命令（check、run、gate、lock / pool lease、decide），报告写明来源。

### 3. 指标的定义
- **墙钟**：一次运行第一条事件到最后一条事件。
- **排队**：一次运行里所有等待区间的并集。等待区间是 `[拿到时刻 − waited_ms, 拿到时刻]`，来自 `slot_acquired`、`machine_lock`（旧全机锁）、`load_ok`。用并集而不是相加：两条通道同时等待时，相加会重复计入（`docs/research/krill-p0-trial.md`「时间与排队」的注释）。**运行** = 墙钟 − 排队。排队占比 = 各运行排队之和 ÷ 各运行墙钟之和。
- **返工轮数**：同一项（场景或套件）在批次里失败或未验证之后，又被运行的次数。同一 worktree 里算（请求者已知时），否则按项目算。kr 自己的自动重跑（单条重跑、高负载整项重跑）不算返工。
- **偶发排行**：每条测试在批次里被判为偶发的次数（`item_end.flaky`），从多到少；高负载整项重跑通过记为「`<项> (whole item)`」。附这一项在批次里运行的次数作分母。
- **判错的判断点**：`reconciliation` 事件里 `supported` 为 false 的决定。
- **判对率**：每类判断（`kind`），以及每个选项：已对账数、成立数、成立数 ÷ 已对账数。还没有对账的决定单独计数，不进分母。效率类判断点按默认继续、待复核的（`review: "pending"`）单独计数。
- **绕弯**：固定的几类，每类有次数和例子，不做推断：
  - `bad_arguments`：参数错误（调用日志）；
  - `kr_error`：调用日志里以 kr 报错结束的调用（不是测试失败）；时间范围里没有调用日志时，用 `run_end.error`。两者不同时用，避免同一次报错算两次；
  - `aborted`：`run_aborted`；
  - `build_failed_in_run`：`kr run` / `kr gate` 里构建失败（本该在 `kr check` 发现）；
  - `no_result`：开始了的项没有结果，运行也没有正常结束或中止的记录（例如 #25 的 ENOENT）；
  - `filter_mismatch`：过滤通过静态核对但在设备上一条也没选中；
  - `products_missing`：运行途中测试产物不见了；
  - `repeat_after_pass`：同一项、同一构建输入（`identity.input_hash`）已经通过，又运行了一次（只有 #29 之后的运行有输入哈希）；
  - `undecided`：判断点到批次结束还没有交回。

### 4. 只提供数据
报告不给建议，不改权限，退出码总是 0（参数错误时 2）。人读输出最后一行说明这一点：是否在宿主里放宽权限由 owner 决定（ADR 0012）。`--json` 带 `schema_version` 和 `decisions`（为空：报告本身没有判断点），字段只加不改。

## 不做
- 不按空闲间隔、分支名推断批次。
- 不把报告结果写回事件，不根据判对率改变任何命令的行为。
- 不改 `kr deliver`、`kr rejudge` 的行为。
