# 0003 机器档案运行时检测；机器是资源提供方

状态：已采纳（2026-10-14）

## 背景
owner 会换机器、也会同时有多台 Mac（性能差的到最新 M 系列）。写死「最多 2 台模拟器」这类数字只适合某一台机器。高负载时曾出现 SIGTRAP 导致整片假失败（pitfalls E1、R5）。

## 决定
- 每次运行检测机器能力（芯片、核数、内存、Xcode 与模拟器运行时）和实时状态（负载、内存压力、磁盘），由此推算各资源容量。机器级配置可按硬件标识手动覆盖。
- 开跑重活前做负载检查，超过阈值就等待，不直接开跑。
- 资源层把「机器」当作资源提供方。第一阶段只有本机；第二阶段增加 SSH 远程提供方（远程装同一个 kr，代码用 git 拉取已推送的分支，结果和事件传回）。
- kr 不判断某台机器「允许」跑什么。用哪台机器、跑什么，是 owner 在配置里的个人选择。

## 参考
Bazel remote execution、buck2 daemon、sccache（bazel-fit.md、rust-cli-prior-art.md）。

## 补充（2026-10-14）：负载先记录，不阻塞

「开跑重活前做负载检查，超过阈值就等待」暂不执行，原因是阈值没有数据支撑：
- 本机今天 1 分钟负载在 14 到 547 之间；负载 547 时 CPU 合计只用了约 600%/800%。macOS 的 load average 含大量等 I/O 的进程，不能代表还剩多少 CPU。
- 按 1.25 × 核数（10）或 2.5 × 核数（20），几乎每个重活都要等满 20 分钟上限，等待换不来可信度。

现在的做法：
- 默认不因负载阻塞（`[load] block = false`）。限制并发的是 kr 的槽位（本机 build 1 / sim 2）和旧全机锁（ADR 0009）。
- 内存压力 critical 时仍然等待（这时在换页，确实会造成假失败），上限 20 分钟。
- 每个场景/套件开始和结束时采样 1/5/15 分钟负载和内存压力，写进 `item_end` 事件和结果。
- 失败发生在高负载期间（1 分钟负载 > `[load] per_core` × 核数，默认 4）时，结果标注「高负载期间失败」，整个场景/套件单独再跑一次：通过记偶发，仍失败记失败。
- `[load] block = true` 可恢复「高负载时等待」（阈值同为 `per_core` × 核数）。

阈值暂无数据支撑，先记录后决策：Krill 第 7 批跑完后，用这些事件计算负载与失败率的关系，再决定是否开启阻塞、阈值多少。

## 补充（2026-10-15，#40，协调者已确认）：确定失败不再整组重跑

- 每次逐个重跑前后都采样负载，用同一个 `overloaded(per_core)` 规则判断。只有两次采样都有结果、都正常，且目标用例再次明确失败，才保留失败证据，不因原场景高负载再跑整个场景或套件。
- 逐个重跑事件写 `load`（start/end）与 `load_state`（normal/high/unknown）。跳过整组的 `rerun` 事件写 `whole_item: true`、`skipped: true`、原因 `persistent test failure after individual rerun under normal load`，并把这次逐个重跑的用例、负载状态和采样放在 `solo_rerun` 作为证据。
- 逐个重跑仍处于高负载或负载未知时，保守保留整组重跑。逐个重跑都通过，或没有能逐个重跑的用例（包括缺少结果、重跑过滤无效、重跑没有目标用例的结果），也保留高负载整项重跑。未运行、缺失结果、负载未知都不能证明用例在正常环境下也会失败。
- 离线重放旧事件时，不能用整个场景的开始/结束负载替代逐个重跑的负载；旧记录没有逐个重跑的采样时，计为保留整组重跑。
- 命令套件首次日志写 `<name>.log`，整项重跑写 `<name>.again.log`；`item_end` 和 `rerun` 记录两份路径，人读报告保留首次失败日志路径。
