# 0026 `kr report` 列出该用 light 的任务

状态：提议（2026-11-14，#66 由 owner 提出，待协调者在 PR 审查时确认）。部分修改 ADR 0016 §4。

## 背景

Conflux 一周 2241 次 `kr lock`，墙钟的 56% 在排队。`conflux-zero-test-guard-test` 持有 build 98 次，最长 12.5 秒，合计 0.1 小时，自己却排队 3.9 小时；它占着唯一的 build 槽位，后面的构建也要等它。这类任务本该用 `light`：`light` 不等负载、不和构建抢槽位。

ADR 0016 §4 规定报告「不给建议」。那条是为了不让报告替 owner 判断信任和权限（ADR 0012）。「这条命令该换哪种资源」不涉及信任，按固定规则就能定，不需要猜。

## 决定

- `kr report` 新增一节 `light_candidates`：只看 `kr lock` 的运行（不含 `kr pool lease`，它需要模拟器），资源是 `build` 或 `sim`，同一 task 在批次里持有至少 5 次，持有时长 p90（最近秩）低于 15 秒。
- 每个 task 给出：次数、p90、最长、持有合计、自己排队合计（`queued_ms`，与「排队」同一定义）、别人因它等待的时长（`others_waited_ms`：它持有槽位期间，其他运行等同一资源的等待区间与之重叠的部分之和），以及建议命令 `kr lock light --task <task> -- <command>`。
- 按 `queued_ms + others_waited_ms` 从大到小排。门槛写成常量，并在 JSON 里给出（`min_holds`、`max_p90_ms`）。
- 报告仍然不改任何东西，退出码不变。建议只来自上面的固定规则；不按规则以外的东西推断。

## 不做

- 不自动把任务改成 `light`，不改 `kr lock` 的行为。
- 门槛暂不做成参数；有了不同项目的数据再说。
- `others_waited_ms` 在容量大于 1 的资源上会高估（等待者可能在等别的槽位），只作排序参考。
